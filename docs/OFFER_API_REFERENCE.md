# Ticket Offer API Reference

## Endpoints

### 1. Release Tickets (Queue Offer Creation)

**Request:**
```http
POST /waitlist/events/:eventId/release-tickets
Content-Type: application/json

{
  "zones": {
    "VIP": 5,
    "General": 10
  },
  "reason": "cancellation"
}
```

**Parameters:**
- `eventId` (path) - Event identifier
- `zones` (body) - Object mapping zone names to ticket quantities
- `reason` (body, optional) - Release reason: `cancellation`, `refund`, or `courtesy_expired`

**Response (202 Queued):**
```json
{
  "event": "tickets_released",
  "job_id": "ticket-release-123",
  "event_id": "concert-2026",
  "zones": [
    {"zone_id": "VIP", "quantity": 5},
    {"zone_id": "General", "quantity": 10}
  ],
  "reason": "cancellation",
  "status": "queued",
  "message": "Ticket release job has been queued for processing"
}
```

**Errors:**
- `400` - Invalid zones format
- `500` - Server error

---

### 2. Accept Ticket Offer

**Request:**
```http
POST /waitlist/offers/{token}/accept
```

**Parameters:**
- `token` (path) - Unique offer token (generated by worker)

**Response (Success - 200):**
```json
{
  "success": true,
  "checkout_url": "https://seatix.com/checkout/ABC123XYZ",
  "expires_in_minutes": 10,
  "tickets_reserved": 2,
  "zone": "VIP",
  "event_id": "concert-2026",
  "user_id": "alice@example.com"
}
```

**Response (Expired/Not Found - 410):**
```json
{
  "success": false,
  "error": "offer_expired",
  "message": "Tu oportunidad expiró. Has sido regresado a la lista."
}
```

**Errors:**
- `400` - Missing token parameter
- `410` - Token expired or doesn't exist (user returned to queue)
- `500` - Server error

## Redis Data Structures

### Offer Storage

```
Key: offer:{token}
Type: String (JSON)
TTL: OFFER_TTL_MINUTES (default: 10 minutes)

Value:
{
  "event_id": "concert-2026",
  "user_id": "alice",
  "zone": "VIP",
  "tickets_reserved": 3,
  "created_at": "2026-02-04T13:45:30.123Z"
}
```

### Queue Storage

```
Key: waitlist:event:{eventId}:zone:{zone}
Type: List
TTL: None (permanent until removed)

Values: "userId:quantity" (FIFO with RPOP)
Example: "alice:3", "bob:2", "charlie:5"
```

## Error Handling

### Status Codes

| Code | Meaning | Action |
|------|---------|--------|
| 200 | Success | User can proceed to checkout |
| 400 | Bad Request | Check request format |
| 410 | Gone | Offer expired, user stays in queue |
| 500 | Server Error | Retry or contact support |

### Error Response Format

```json
{
  "success": false,
  "error": "error_code",
  "message": "Human-readable message (Spanish for users)"
}
```

## Flow Examples

### Example 1: User Accepts Offer
```
1. POST /waitlist/offers/a1b2c3d4/accept
2. Redis checks: PTTL offer:a1b2c3d4 (exists, TTL > 0)
3. Redis deletes: DEL offer:a1b2c3d4
4. Return checkout URL
5. User cannot reuse token (already deleted)
```

### Example 2: User Accepts Expired Offer
```
1. POST /waitlist/offers/a1b2c3d4/accept
2. Redis checks: PTTL offer:a1b2c3d4 (doesn't exist, expired)
3. Return 410 offer_expired
4. User is NOT returned to queue (already status='notified')
5. User must contact support or re-join waitlist
```

### Example 3: Partial Quantity Fulfillment
```
Queue: alice:3, bob:10, charlie:2
Release: 5 tickets

1. Worker iterates from end (FIFO)
2. alice needs 3, available 5 ✓ ACCEPT, create offer
3. bob needs 10, available 2 ✗ SKIP, stays in queue
4. charlie needs 2, available 0 ✗ SKIP, stays in queue

Result: Only alice notified with offer
Next release can notify bob or charlie based on quantity
```

## Configuration

### Environment Variables

```bash
# Offer validity period (minutes)
OFFER_TTL_MINUTES=10

# Redis connection
REDIS_URL=redis://redis:6379

# Database
SQLITE_PATH=/data/waitlist.db

# Server
PORT=3000
```

### Changing Offer Duration

For testing with shorter TTL:

```bash
# Docker
docker compose up -e OFFER_TTL_MINUTES=1

# Or in docker-compose.yml
environment:
  - OFFER_TTL_MINUTES=5
```

## Workflow: User Gets an Offer

```
USER REGISTRATION
POST /waitlist/events/{eventId}/waitlist
├─ body: {user_id, zones_preferred, quantity_wanted}
└─ response: entry_id, positions

                ⏸️ User waits in queue

TICKETS RELEASED
POST /waitlist/events/{eventId}/release-tickets
├─ body: {zones, reason}
└─ response: job queued

WORKER PROCESSES
├─ Pulls eligible users from Redis
├─ Checks: available >= user.quantity_wanted
├─ Creates offer token if eligible
├─ Stores in Redis with TTL
└─ Updates SQLite: status='notified'

                📧 Email sent (future integration)
                   "Click here to buy: /waitlist/offers/{TOKEN}/accept"

USER ACCEPTS OFFER
POST /waitlist/offers/{TOKEN}/accept
├─ Check Redis: offer exists?
├─ YES: Delete token (single-use), return checkout URL
└─ NO: Return 410 offer_expired

CHECKOUT
User goes to checkout URL provided in response
```

## Security Notes

- ✅ Tokens are 128-bit random (cryptographically secure)
- ✅ Single-use (deleted immediately after acceptance)
- ✅ Time-limited (expires after OFFER_TTL_MINUTES)
- ✅ No persistent storage (ephemeral in Redis)
- ✅ Cannot be guessed (32-char hex, 2^128 possibilities)

**Limitations:**
- ⚠️ No user authentication (still using headers)
- ⚠️ No rate limiting per user
- ⚠️ No audit logging of acceptance
